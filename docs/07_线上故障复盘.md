# 07 · 线上故障复盘：INC-0421 订单查询 Agent 深夜死循环

> 说明：这是一个按真实事故模式**构造**的案例，不是某家公司的真实事件。它的每一步都能在本项目里复现（`examples/05_incident_replay.py`），数字都是实测。面试时要讲你自己的故障；本文末尾给出了把它变成自己经历的方法和讲述模板。

## 摘要

| 项 | 内容 |
|---|---|
| 影响 | 客服 Agent 单个会话消耗 40,970 token（正常一轮约 1,500），模型调用 31 次；同类会话在 02:00–02:40 之间出现多个 |
| 触发 | 上游订单服务 02:00 发布，订单号格式从 `SO-000123` 改为 `SO-123`，旧格式查询返回 HTTP 200 + `{"code":"NOT_FOUND","message":"... please retry later"}` |
| 根因 | ① 工具把上游 body 原样透传，错误文案里的 "please retry later" 诱导模型重试；② 守护层只有 max_rounds=30，没有同工具同参数检测；③ 工具没有结果 schema 校验，上游契约变更没有被发现 |
| 发现方式 | 成本告警：单会话 token > P99 × 10 |
| 恢复时间 | 止血 5 分钟（降 max_rounds + 熔断降级），根因修复当天上线 |

## 时间线

| 时间 | 事件 |
|---|---|
| 02:00 | 订单服务发布 v2.14，订单号去前导零，旧格式返回 NOT_FOUND |
| 02:07 | 第一个受影响会话开始：用户问"我的订单 SO-000123 到哪了？" |
| 02:13 | 成本告警触发：会话 inc0421-naive tokens 40,970 > 阈值 |
| 02:20 | 值班拉 trace，确认死循环模式 |
| 02:25 | 止血：max_rounds 30 → 8，lookup_order 熔断降级为"请稍后再试" |
| 02:40 | 关联到订单服务发布，确认契约变更 |
| 当天 | 同参数检测、错误分类、结果校验、订单号归一化上线 |
| 当周 | 契约测试、新告警、Bad Case 回归 |

## 1. 发现

不是用户投诉，是**指标**。每个会话的 token 消耗从 `turn.end` 事件累加，告警阈值是 P99 的 10 倍。02:13 触发。

反事实：如果没有 per-session token 指标，这些会话会安静地跑到 max_rounds=30 才停，第二天看账单才知道。这就是"只跑过 demo 的人讲不出发现那一环"的原因——demo 里没有这个指标。

`examples/05` 阶段 1 的输出：

```
会话 inc0421-naive: 模型调用 31 次, 工具调用 30 次, tokens 40970, 估算成本 $0.2186, 停止原因 loop_stop
```

## 2. 定位

拉出这个 run_id 的 trace，三条查询：

**① 工具调用按 (工具, 参数) 聚合**
```
30 × lookup_order {"order_id": "SO-000123"}
```
同一个参数 30 次。这一步就能确定是死循环，而且是"同参数"死循环，不是模型在探索。

**② 第一次工具返回，模型看到了什么**
```json
{"ok": true, "data": {"code": "NOT_FOUND", "message": "order SO-000123 not found, please retry later"}}
```
注意 `ok: true`——工具层把上游 200 当成成功，把 body 原样当 data。模型看到 "please retry later"。

**③ 模型每一步说的话**
```
'让我再试一次。': 29 次
```

**④ 和变更对时间**：订单服务 02:00 发布，发布说明写着"订单号格式统一去前导零"。用新格式 `SO-123` 手动查，成功。

根因确认三条：
1. 工具层没有错误分类：业务错误（NOT_FOUND）被当成成功数据透传；上游文案直接影响模型行为。
2. 守护层只有步数上限：每一步上下文都在变长（输入 tokens 552 → 596 → 647 → … → 1741），消耗二次方增长，烧到上限才停。
3. 工具层没有结果 schema 校验：契约变更（字段从订单信息变成 code/message）没有触发任何告警。

## 3. 修复

按时间尺度分三层，每层都有证据。

### 3a 止血（分钟级）
- max_rounds 30 → 8：单会话最坏损失降到约四分之一。
- lookup_order 熔断打开，降级为"订单服务暂时不可用，请稍后再试"。

What-if 重放验证：用当时 trace 里记录的工具结果、同一个固执模型、只加同参数检测：

```
3a 止血（只加同参数检测，工具不改，用当时记录的工具结果 what-if 重放）: 4 次模型调用即停, tokens 2577
```

在改工具之前就知道止血方案有效。

### 3b 短期修复（当天）
- **同工具同参数检测**：连续第 2 次注入提醒、第 3 次强制收尾；累计第 4 次（防交替）；连续 4 次结果哈希相同（无进展）。触发后进收尾模式，不给工具，要求用现有信息作答。
- **错误分类 + hint**：`lookup_order_v2` 把 NOT_FOUND 分类为永久错误，信封 `retryable: false`，hint 是"订单号可能有误，请向用户核对订单号（格式 SO-数字），不要重复用同一个订单号查询"。
- **结果 schema 校验**：`result_model=OrderInfo`，上游再改契约会直接产生 `alert`。

修复后模型看到的第一次工具返回：
```json
{"ok": false, "error": {"kind": "permanent", "message": "订单 SO-000123 不存在", "retryable": false,
 "hint": "订单号可能有误，请向用户核对订单号（格式 SO-数字），不要重复用同一个订单号查询"}}
```

### 3c 根因修复（当周）
- 订单号归一化：`normalize_order_id("SO-000123") == "SO-123"`，兼容上游改格式前后的写法。
- 上游契约纳入契约测试：订单服务的响应结构变化在它的 CI 就会失败。
- 错误文案审查：工具返回给模型的任何文案里不得出现 "retry" / "try again"，除非真的希望模型重试。

| | 模型调用 | tokens | 成本（opus-5 价） |
|---|---|---|---|
| 事故前 | 31 | 40,970 | $0.2186 |
| 只加守护（what-if） | 4 | 2,577 | $0.0147 |
| 根因修复 | 4 | 2,792 | $0.0158 |

## 4. 防复发

- **Bad Case**：`badcases/BC-001_same_args_loop.json`——复现条件（固执模型 + retry_later 故障）、输入、断言（≤5 次调用、同参数 ≤3 次、≤6000 token、不转人工、回复里有"抱歉"或"人工"）。永远跑。
- **区分度验证**：同一用例换回事故前配置必须不通过：`rounds 31 > 5, same-call repeats 30 > 3, tokens 40970 > 6000`。
- **新告警**：per-turn 模型调用次数 > 10；`guard.loop` stop 事件；`tool.result.error_kind == invalid_result`。
- **流程**：上游服务发布说明里涉及响应结构变化的，必须通知 Agent 团队（这一条是最难落实的，所以契约测试才重要）。

## 5. 教训

1. 模型看到的每一个字都是提示词，包括错误文案。
2. 最大步数是最后一道闸，不是第一道。越晚停越贵，因为上下文在长。
3. "上游返回 200"不等于成功。工具层必须做业务错误分类和结果校验。
4. 发现靠指标，定位靠 trace，修复靠重放验证，防复发靠回归用例。四样都要有。

## 把它变成你自己的故事

面试官听的是三个东西：**发现那一环的具体指标**、**定位时你跑的那条具体查询**、**修复前后那一个具体数字**。三样都具体，就是真的。

### 演练（一小时）

1. 跑 `python examples/05_incident_replay.py`，看完整流程。
2. 打开 `agentkit/harness.py`，把 `GUARDED_LOOP` 改成和 `NAIVE_LOOP` 一样；跑 `pytest tests/test_replay_badcase.py`，看 BC-001 变红，看 metrics 里的数字。
3. 打开 `examples/out/inc0421_before.jsonl`，用 `load_trace` 自己写三条查询把根因找出来（别看阶段 2 的代码）。
4. 改回 `GUARDED_LOOP`，再把 `same_call_stop_at` 调成 2、5、10，分别看 BC-001 的 rounds 和 tokens，理解阈值为什么是 3。
5. 把 `lookup_order_v2` 里的 hint 改成含 "please retry"，跑 `test_stubborn_model_is_stopped_by_same_call_detector`，看守护层怎么兜住模型层的问题。

做完这五步，"讲一次线上故障"时你至少有一次亲手定位和修复的经历，细节是自己的。

### 讲述模板（两分钟）

> 背景一句话：什么系统、什么工具、什么流量。
> 发现：几点、什么指标、什么阈值触发了告警；如果没有这个指标会怎样。
> 定位：拉了哪个会话的 trace；按什么聚合；看到了什么模式（同参数 N 次）；模型看到的那条返回长什么样；和哪个变更对上了时间。
> 修复：止血做了什么、几分钟；短期修了什么、怎么验证的（what-if 重放）；根因修了什么。
> 数字：修复前后各一个。
> 防复发：回归用例 + 新告警 + 一条流程。
> 教训一句话。

如果你有真实经历，把它套进这个模板；如果只有本项目的演练，如实说"这是我在一个教学项目里完整复现过的事故模式"，然后把细节讲透——细节比来源更能分辨人。
