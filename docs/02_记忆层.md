# 02 · 记忆层：多轮对话的信息损耗怎么管

对应代码：`agentkit/memory/`，测试：`tests/test_memory.py`，示例：`examples/02_memory_turn20.py`。

## 1. 三层记忆

| 层 | 内容 | 有损？ | 回答的问题 | 代码 |
|---|---|---|---|---|
| 工作记忆 | 最近几轮对话原文（含工具调用与结果） | 否，但有上限 | 刚才说到哪了 | `MemoryManager.working` |
| 情景摘要 | 更早轮次的压缩摘要 | 是 | 之前大概聊了什么 | `MemoryManager.summary` |
| 长期事实 | 从对话抽取的结构化事实（订单号、过敏、预算…） | 否 | 用户的硬约束是什么 | `tiers.py::LongTermMemory` |

"第 20 轮丢了第 1 轮的信息"几乎都是：第 1 轮原文被压缩进摘要时丢了，而这个信息又没有落到第三层。所以第三层里 `pinned=True` 的事实在组装上下文时**永远带上，不参与预算竞争**。

## 2. 一轮对话里记忆的读写顺序

```
mm.start_turn(user_text)   写：抽取事实 → 长期记忆（memory.fact_upsert 事件）；user 消息进工作记忆
mm.build_context(...)      读：召回（pinned 全部 + 相关 top-k）+ 摘要 + 工作窗口 → 在预算内组装（context.built 事件）
mm.append(...)             主循环产生的 assistant / tool 消息
mm.end_turn()              工作记忆超过高水位 → 压缩旧轮次进摘要（memory.compress 事件）
```

这也回答了"模型是直接调 API 还是先走记忆检索"：**每次调模型前都先走记忆**，`build_context` 就是那一步。

## 3. 写入侧：抽取

- `RuleFactExtractor`：正则规则，零成本、确定、可测。覆盖订单号（并归一化 SO-000123 → SO-123）、手机号、姓名、过敏、预算、地址（pinned），时限、忌口（非 pinned）。
- `LLMFactExtractor`：让模型输出 JSON 事实列表，覆盖长尾；解析失败返回空，抽取失败不能影响主流程。
- `CompositeExtractor`：规则先跑，LLM 补充，按 (key, value) 去重。

生产上的常见做法：规则每轮都跑；LLM 抽取异步跑，或只在用户消息较长时跑。

多个同类事实（两个订单号）用 `multi=True`，存成 `订单号` / `订单号#2`；单值事实（预算）后说的覆盖先说的，来源轮次更新。

## 4. 读取侧：召回

`LongTermMemory.recall(query, k, current_turn)`：pinned 全部返回；其余按与 query 的字符 2-gram 重叠打分，加一点近因与命中次数，取 top-k，重叠为 0 的不返回。

项目刻意不依赖向量库。生产换 embedding 时结构不变：**pinned 永远带上 + 其余按相关性**。真正容易出问题的不是打分算法，而是该 pinned 的没 pinned（`test_diagnosis_distinguishes_not_recalled_for_unpinned_fact`：忌口"香菜"没被召回，因为问题里没有相关词，而它也没有 pinned）。

## 5. 压缩：有损，所以要有保底

触发：`end_turn` 时工作记忆 token 超过 `working_high_water_tokens`；保留最近 `keep_recent_turns` 轮原文，更早的交给摘要器。

摘要器接口 `summarize(previous_summary, messages, must_keep, max_tokens)`：
- `must_keep` 是所有 pinned 事实的值（`pin_facts_in_summary=True` 时）；
- 摘要器自己尽量保留；**压缩后再由代码 `ensure_facts_present` 校验，缺了就补一行「关键信息」**；
- `ExtractiveSummarizer` 是确定性实现（每条消息截前 60 字，超长时丢最旧片段），`LLMSummarizer` 用模型做，失败退回抽取式。

`memory.compress` 事件记录：哪些轮被压、摘要多长、补回了哪些事实。"信息是在压缩时丢的"能被证明，不是猜。

`keep_facts=False` 的摘要器 + `NullExtractor` 就是 naive 配置：`test_naive_summarizer_loses_facts_when_not_told_to_keep`。

## 6. 上下文组装：预算内的优先级

`context_builder.build_context` 的裁剪顺序（从低优先级开始裁）：

1. 系统提示（稳定部分）—— 不裁
2. 关键信息块（pinned + 召回事实）—— 不裁
3. 早先对话摘要
4. 工作记忆原文 —— 从最旧的开始裁，**以完整轮次为单位，永不拆开 assistant 的 tool_calls 和对应的 tool 结果**，第一条必须是普通 user 消息

`ContextReport` 记录各段 token、包含/裁掉的轮次、pinned 与召回的键、关键信息块全文，写进 `context.built` 事件。这是排查"模型为什么不知道 X"的第一手证据。

测试：`test_context_builder_trims_oldest_and_never_splits_tool_groups`、`test_context_builder_pinned_facts_do_not_compete_with_budget`。

## 7. 排查路径：把它写成代码

`diagnose.py::diagnose_missing_fact(events, fact_value, at_turn, aliases)`：

```
用户说过吗?（turn.start）              否 → never_stated
写入：抽取到长期记忆了吗?（fact_upsert）
读取：第 N 轮 context.built 里有它吗?
   在 memory_block 或 included_turns 里 → present_in_context   （不是记忆层的问题）
   没有 & 没抽取                        → not_extracted        （补抽取规则 / LLM 抽取 / 标 pinned）
   没有 & 抽取了但未 pinned             → not_recalled         （标 pinned / 改召回打分）
   没有 & 原文轮次被压缩且摘要没有      → lost_in_compression  （must_keep + ensure_facts_present）
   没有 & 原文被预算裁掉                → trimmed_from_window  （pinned 事实进关键信息块）
```

`examples/02_memory_turn20.py` 的实际输出：

- naive：第 20 轮回答"抱歉，我不记得您的订单号了"，诊断 `not_extracted`（第 1 轮在第 9 轮被压缩，摘要到第 20 轮已把它丢掉，长期记忆里也没有）。
- guarded：第 20 轮回答"您的订单号是 SO-123"，诊断 `present_in_context`，证据是 `in_memory_block=True, in_window=False`——原文早不在窗口，靠关键信息块。

`aliases` 参数是因为归一化：用户说 SO-000123，存的是 SO-123，两个写法都要查。

## 8. 和提示词缓存的关系

上下文布局直接决定缓存命中率（缓存是前缀匹配，断点之前任何字节变化都会让缓存失效）：
- `build_context` 把系统提示分成两块 `system_blocks = [稳定系统提示, 记忆块]`；适配器只在第一块打缓存断点（`anthropic_client.py::to_anthropic_system`），记忆块作为第二块不打断点。记忆块（召回结果）变了，稳定前缀的缓存仍然命中；如果把两者拼成一个字符串再打断点，记忆块就进了前缀，每次召回变化都会让系统提示的缓存失效——这正是下面说的"隐形失效源"（`test_client_request_shape_with_stub` 锁定了这个布局）；
- 工作窗口以轮次为单位整块裁剪，不要每轮滑一条（每滑一条前缀就变一次）；
- 工具列表按名字排序（`ToolRegistry.schemas`），顺序抖动等于全量失效；
- 最后一条消息打移动断点，同一轮里多次工具往返命中前缀。

用 `usage.cache_read_tokens` 验证：连续请求一直是 0 说明有隐形失效源（时间戳、UUID、未排序 JSON）。

## 9. 生产上还要做的

- 长期事实按用户持久化（会话开始加载 pinned），支持用户查看与删除；
- 事实有时效：地址会变，pinned 事实带 `source_turn`，冲突时新的覆盖旧的并记录；
- 摘要用模型做时，摘要器的输出也要过一遍内容审核和 must_keep 校验；
- 厂商侧的服务端压缩（Anthropic compaction）可以替代自研摘要，但 pinned 事实层仍然要自己管——服务端不知道哪些是你的硬约束。
