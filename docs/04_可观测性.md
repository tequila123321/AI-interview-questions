# 04 · 可观测性：trace、重放、Bad Case 闭环

对应代码：`agentkit/observability/`，测试：`tests/test_replay_badcase.py`，示例：`examples/05_incident_replay.py`（阶段 2 和 4）。

## 1. 结构化 trace（`trace.py`）

不是日志，是事件：每条带 `seq / ts / run_id / turn / step / kind` 和该事件的字段，JSONL 追加写。

| kind | 关键字段 | 用来回答 |
|---|---|---|
| `turn.start` / `turn.end` | user_text；rounds, stop_reason, handoff, tokens, guard_events | 这一轮怎么结束的 |
| `context.built` | 各段 token、included/dropped_turns、pinned/recalled_keys、memory_block | 模型这次到底看到了什么 |
| `llm.request` / `llm.response` | fingerprint；text, tool_calls, usage, stop_reason, latency_ms | 模型每一步说了什么、花了多少 |
| `llm.retry` / `llm.failed` | attempt, delay_s, error | 模型服务抖动 |
| `tool.call` / `tool.attempt` / `tool.retry` / `tool.result` | args；attempt, ok, latency；delay_s；payload, result_hash, error_kind, degraded | 工具链路每一跳 |
| `guard.loop` / `guard.budget` / `guard.content` / `guard.assertion` | action, reason | 哪道闸在什么时候动了 |
| `memory.fact_upsert` / `memory.compress` | key, value, pinned；dropped_turns, summary, missing_fixed | 记忆写入与压缩 |
| `alert` | severity, reason | 需要人看的事 |
| `workflow.node` / `workflow.retry` / `workflow.compensate` / `workflow.failed` | node, status, attempt | 工作流每个节点 |
| `handoff` | reason, stop_reason | 为什么转人工 |

`Tracer.find(kind, **match)` 做内存查询；`load_trace(path)` 读回 JSONL。

### 定位一次事故时怎么查

`examples/05_incident_replay.py` 阶段 2 就是三条查询：
1. `tool.call` 按 (tool, args) 聚合 → 30 × lookup_order {"order_id": "SO-000123"}
2. 第一条 `tool.result` 的 payload → 模型看到了 "please retry later"
3. `llm.response` 的 text 计数 → 29 次"让我再试一次。"

## 2. 该设的指标与告警（从 trace 派生）

| 指标 | 来源 | 告警建议 |
|---|---|---|
| per-session tokens / 成本 | `turn.end.tokens` 累加 | > P99 × N |
| per-turn 模型调用次数 | `turn.end.rounds` | > 10 |
| 同参数重复调用数 | `guard.loop` 或离线按 tool.call 聚合 | ≥ 3 |
| 工具错误率按 kind | `tool.result.error_kind` | invalid_result 出现即告警（契约变更） |
| 降级率 / 转人工率 | `tool.result.degraded`、`handoff` | 突增 |
| 断言失败数 | `guard.assertion.passed=false` | hard 失败即告警 |
| 缓存命中率 | `llm.response.usage.cache_read_tokens` | 连续为 0 |
| stop_reason 分布 | `turn.end.stop_reason` | loop_stop / budget_stop 占比上升 |

事故里"发现"那一环，就是第一行那个指标。

## 3. 日志重放（`replay.py`）

### 忠实重放

模型响应和工具结果都从 trace 取：

```python
events = load_trace("trace.jsonl")
report = replay(events, agent_factory, registry, strict=True)
report.matched, report.diffs
```

- `ReplayLLM` 按记录顺序返回 `llm.response`；strict 模式校验每次请求指纹与当时一致，不一致抛 `ReplayDivergence`——说明上下文构建逻辑变了，这本身是有价值的信号（`test_strict_replay_detects_context_logic_change`）。
- `RecordedToolExecutor` 按 (tool, args 哈希) 队列返回 `tool.result` 的 payload。
- 用途：线上坏结果本地单步复现，不用真模型、不用真下游；可以挂上新断言看"当时会不会被拦住"。

### What-if 重放

工具结果从记录取，模型换成刻画其行为的策略，守护层换新配置：

```python
rec_exec = RecordedToolExecutor(events, registry, tracer)
Agent(FakeLLM(policy=stubborn_policy), rec_exec, MemoryManager(), loop_policy=GUARDED_LOOP, ...)
```

`examples/05` 阶段 3a：只加同参数检测、工具不改，用当时记录的工具结果重放 → 4 次调用即停。这是"止血方案能不能用"的证据，在改工具之前就能得到。

## 4. Bad Case 闭环（`badcase.py`、`badcases/*.json`）

一个 Bad Case 描述三件事：

```json
{
  "id": "BC-001",
  "title": "上游 NOT_FOUND 文案含 'please retry later'，模型用同一订单号反复查询直到步数上限",
  "origin": "docs/07_线上故障复盘.md（INC-0421）",
  "profile": "guarded", "policy": "stubborn",
  "tool_faults": {"lookup_order": ["retry_later"]},
  "user_turns": ["我的订单 SO-000123 到哪了？"],
  "expect": {"max_rounds": 5, "max_same_call_repeats": 3, "max_total_tokens": 6000,
             "must_handoff": false, "final_must_contain_any": ["抱歉", "人工"]}
}
```

1. **复现条件**：模型行为（policy）+ 下游故障（tool_faults）
2. **输入**：用户轮次
3. **修复后必须满足**：步数、同参数重复、token、必须/不得说什么、是否转人工

`tests/test_replay_badcase.py::test_badcase_regression` 对 `badcases/` 目录参数化，每个文件永远跑。`test_badcase_would_fail_on_naive_profile` 证明用例有区分度：同一用例换回事故前配置必须不通过（实测 rounds 31 > 5, repeats 30 > 3, tokens 40970 > 6000）。

闭环的意思：线上坏结果 → 事故复盘 → Bad Case 文件 → 回归。以后任何人调守护层参数、换模型、改提示词，回归会说话。

三个内置用例分别覆盖：同参数死循环（BC-001）、写操作参数编造被断言拦下（BC-002）、非关键工具超时应降级而非报错（BC-003）。

## 5. 面试时的一句话版本

"每个动作都是一条结构化事件，所以线上坏结果能拉出完整时间线、能离线重放（忠实重放复现，what-if 重放验证方案）、能变成一个 Bad Case 文件永远回归；告警来自这些事件派生的指标，比如单会话 token 超 P99 十倍。"
