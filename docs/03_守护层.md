# 03 · 守护层：不靠模型听话，靠代码卡住

对应代码：`agentkit/guard/`、`agentkit/agent.py`，测试：`tests/test_loop_detector.py`、`tests/test_guards_units.py`、`tests/test_agent_guards.py`，示例：`examples/03_loop_guard.py`。

## 1. 死循环：为什么只有最大步数不够

`examples/03_loop_guard.py` 的实测（同一个"固执"模型、同一个上游故障：订单服务返回 200 + "please retry later"）：

| 配置 | 模型调用 | 工具调用 | 总 tokens | 估算成本（opus-5 价） |
|---|---|---|---|---|
| naive：只有 max_rounds=30 | 31 | 30 | 40,970 | $0.2186 |
| guarded：同参数检测 | 4 | 3 | 2,792 | $0.0158 |

naive 每一步的模型输入 tokens：552, 596, 647, 698, 749, 800 … 1741。每一步都把上一步的工具结果堆进上下文，**总消耗随步数二次方增长**。max_rounds 越大，"烧完才停"越贵。

### 三种更早的检测（`guard/loop_detector.py`）

| 检测 | 判定 | 默认阈值（GUARDED_LOOP） |
|---|---|---|
| 同工具同参数**连续**调用 | canonical 键 = 工具名 + 参数排序后哈希；数尾部连续相同 | 第 2 次 warn，第 3 次 stop |
| 同工具同参数**累计**调用 | 防 A-B-A-B 交替 | 第 4 次 stop |
| 无进展 | 连续 N 次工具结果哈希相同（不同调用也算） | 4 次 stop |
| 最大步数 | 一轮里模型调用次数 | 10 |

canonical 键用排序后哈希，`{"a":1,"b":2}` 和 `{"b":2,"a":1}` 是同一个调用（`test_canonical_key_ignores_dict_order`）。

### 触发后做什么（`agent.py::run_turn`）

- **warn**：仍然执行工具，但把提醒写进信封的 `guard_note`："这是你第 2 次用相同参数调用 X，如果结果仍然相同，不要再重复……"。模型能看见自己在原地打转。
- **stop**：不执行；写一条 `loop_detected` 错误；Agent 进入**收尾模式**：下一次模型调用不给工具列表，并追加一条系统指令要求用现有信息作答。模型仍然要调工具 → 转人工。

为什么先提醒再停而不是第 2 次就停：有些工具第二次真的会不一样（刚写入再读）。阈值是经验值，`LoopPolicy` 可调；改了阈值跑 `tests/test_replay_badcase.py`，Bad Case 会告诉你有没有把哪个事故的坑又挖开。

## 2. 内容安全（`guard/content_filter.py`）

两条方向：

**出向（模型 → 用户）**，`check_output`：
1. 规则：违禁词 → block；PII（手机号、身份证、银行卡、邮箱）→ redact（掩码 `138****5678`）；
2. 可插拔 LLM 审核 `judge(text) -> (is_safe, reason)`：覆盖语义违规；有成本有延迟，通常只对最终回复做；
3. 动作 pass / redact / block；block 时替换为固定兜底话术，不让半截违规内容漏出去。

**入向（模型 → 工具）**，`check_tool_args`：模型可能把用户在对话里说过的手机号原样塞进搜索类工具的参数发给第三方。对声明为 `pii_free_tools` 的工具做参数脱敏（`test_tool_args_pii_is_redacted_before_leaving_the_system`）。

每一次非 pass 的判定都记 `guard.content` 事件：误杀率要能复盘。

## 3. 成本控制（`guard/budget.py` + 上下文构建 + 缓存）

三级上限，各管一件事：

| 级别 | 机制 | 位置 |
|---|---|---|
| 单次请求输入 | 上下文构建器在预算内裁剪 | `AgentConfig.context_budget_tokens` |
| 单轮累计 | 一轮里模型来回调工具的总消耗 | `BudgetPolicy.max_tokens_per_turn` |
| 会话成本 | 硬止损 | `BudgetPolicy.max_cost_usd_per_session` |

到 `wrap_up_ratio`（默认 80%）时不是掐断，而是进收尾模式：用户拿到的是一个降级但完整的回复，不是半截话。到 100% 且模型还想调工具 → 转人工（`test_budget_stop_with_pending_tool_calls_hands_off`）。

成本 = 输入 × 输入单价 + 输出 × 输出单价 + 缓存读 × 缓存读单价 + 缓存写 × 缓存写单价（默认按 claude-opus-5：$5 / $25 / $0.50 / $6.25 每百万 token，`Budget.cost_of`）。缓存读只有输入价的十分之一，所以**提示词缓存是最大的成本杠杆**：

- 缓存是前缀匹配，断点之前任何字节变化都让缓存失效；
- 稳定内容在前打断点（系统提示第一块、工具列表），波动内容在断点之后（记忆块作为第二个 system 块、最新消息）；
- 隐形失效源：系统提示里的时间戳、UUID、`json.dumps` 没 `sort_keys`、工具列表顺序抖动；
- 验证方式：看 `usage.cache_read_tokens`，连续请求一直为 0 就有问题。

上下文裁剪与压缩见 `docs/02` 第 6、8 节。

## 4. 关键节点断言（`guard/assertions.py`）

在确定性的位置用代码卡住模型的不确定性：

| 断言 | 阶段 | 规则 | 严重度 |
|---|---|---|---|
| `refund_target_must_come_from_lookup` | before_tool | 退款订单号必须出现在本会话 lookup_order 成功返回过的集合里 | hard → 转人工 |
| `final_answer_not_empty` | before_final | 回复非空 | hard |
| `pinned_facts_survive_compression` | after_compress | 压缩后摘要含全部 pinned 事实 | soft → 只记录 |

`test_refund_requires_prior_lookup_assertion_blocks_fabricated_order`：模型直接对一个没查过的订单发退款，被拦下转人工，账本里没有任何写入。

断言结果全部进 `guard.assertion` 事件。Bad Case 复盘时能看到"哪一道闸没拦住"。

## 5. 一轮对话里守护层的位置（`agent.py`）

```
on_round（步数）
build_context（预算内）
call_llm（模型层重试）
budget.charge → stop/wrap_up
无工具调用 → before_final 断言 → 输出审核 → 结束
有工具调用 → 每个调用：
    loop_detector.observe → warn 注入 / stop 收尾
    before_tool 断言 → hard 失败转人工
    入参脱敏
    executor.execute（工具层）
    handoff → 转人工
end_turn → 压缩 → after_compress 断言
```

所有分支都有 `TurnResult.stop_reason`（end_turn / loop_stop / budget_stop / handoff / refusal / llm_error）和 `guard_events`，`turn.end` 事件里也有，方便按停止原因聚合看比例。

## 6. 面试时的一句话版本

"死循环我做四层：同参数连续、同参数累计、结果无进展、最大步数，触发先提醒再收尾再转人工，实测同一个故障 31 步 4 万 token 降到 4 步 2.8 千；内容安全出向审核入向脱敏；成本三级预算到 80% 进收尾模式，缓存靠稳定前缀；关键节点用断言卡写操作。"
