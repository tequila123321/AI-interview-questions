# 00 · 面试问题清单与回答骨架

帖子原文的每一个追问 + 评论区两条补充。每题四段：**在考什么 / 回答骨架 / 项目里的证据 / 追问预判**。
骨架不是背诵稿，是回答的顺序：先给结论，再给机制，最后给一个你踩过的坑。

## Q1 模型调工具报错、参数不符合 schema、下游服务超时，代码层面怎么做异常处理？

**在考什么**：你有没有把"失败"当成一等公民设计过。"try-except 捕获一下"暴露的是只跑过正常路径。

**回答骨架**
1. 先分类，再决定动作。三类错误来源不同，动作完全不同：
   - **模型的错**（参数不符合 schema）：用 pydantic 校验，把字段级错误作为结构化结果还给模型让它自己改，不重试、不降级；
   - **下游的抖动**（超时、5xx、限流）：幂等操作按指数退避 + 抖动重试，尊重 Retry-After，重试次数有上限；
   - **下游的确定性失败**（404、业务拒绝、返回结构不符合契约）：不重试，走降级。
2. 重试之外还要有熔断：连续失败打开断路器，直接快速降级，给下游恢复时间，也保护自己的线程池。
3. 降级按工具关键程度分：非关键信息给默认值并标记 degraded；关键写操作失败转人工；其余把结构化错误交给模型。
4. 模型看到的永远是结构化信封 `{ok, data | error:{kind, message, retryable, hint}}`。`retryable` 明确告诉模型再试有没有意义，`hint` 告诉它没意义时该干什么。

**项目里的证据**：`tools/errors.py`（分类）、`tools/executor.py::ToolExecutor._execute`（8 步链路）、`tools/retry.py`（退避、熔断）。
测试：`test_tools_executor.py` 每个函数名就是一条规则；`examples/01_tool_failures.py` 打印 9 种情况下模型收到的信封。

**追问预判**
- "非幂等操作怎么重试？" → 执行器不重试；靠幂等键（`RefundArgs.idempotency_key`），同键重复请求返回上次结果。
- "重试耗尽后模型会不会自己再试？" → 耗尽后信封的 retryable 被改成 false 并注明"已自动重试 N 次"（`_degrade`）。
- "超时怎么实现的？" → 真正的超时必须在 I/O 客户端上（httpx timeout）；`run_with_timeout` 是最后一道防线，且 Python 杀不掉线程，这一点要说清楚。

## Q2 模型是直接调 API，还是先走记忆检索？工具返回结果做不做格式校验？

**在考什么**：请求链路是不是清楚，还是"模型自己看着办"。

**回答骨架**
1. 每次调模型之前先走记忆：用本轮用户输入去长期记忆召回（pinned 事实全部带上 + 相关事实 top-k），加上早先对话摘要和最近几轮原文，在 token 预算内组装上下文，然后才调模型。这个组装过程本身产生一份报告（各段 token、召回了哪些、裁掉了哪些）写进 trace。
2. 工具返回一定做 schema 校验。校验失败说明上游契约变了，这是下游的错，不能把垃圾喂给模型让它"猜"，要降级 + 告警。
3. 幂等读工具的结果在会话内缓存，同参数不重复打下游。

**项目里的证据**：`memory/manager.py::build_context`、`memory/context_builder.py`（`ContextReport`）、`tools/registry.py::ToolSpec.result_model`、`tools/executor.py`（结果校验 + `alert` 事件）。

**追问预判**
- "召回怎么打分？" → 项目用字符 2-gram 重叠（零依赖），生产换 embedding，但"pinned 永远带上 + 其余按相关性"的结构不变。
- "契约校验会不会太严导致误伤？" → 校验的是你依赖的字段（pydantic 模型只声明用到的字段，允许额外字段）；上游加字段不会失败，改名/缺失才失败，而这正是该失败的时候。

## Q3 真正落地过的人会讲：超时重试指数退避、结果 schema 校验、异常链路降级到人工兜底或默认返回值

这一条是 Q1/Q2 的答案清单，能讲出**为什么**才算过：
- 指数退避为什么要抖动：一批实例同时重试会把刚恢复的下游再打死（`RetryPolicy.delay_for` 的 full jitter）。
- 为什么要区分默认值降级和转人工：天气查不到给 unknown 没关系，退款失败给"默认成功"是事故（`get_weather.fallback` vs `refund_order.handoff_on_failure`）。
- 为什么降级要标记：模型必须知道这是降级值，才能如实告诉用户"信息可能不完整"（信封里的 `degraded` + `note`，`test_degraded_tool_result_is_surfaced_to_user`）。

## Q4 对话到第 20 轮，Agent 丢失了最早的关键信息，排查路径是什么？

**在考什么**：有没有处理过多轮对话的信息损耗，还是只在接口层打转。

**回答骨架**
1. 先说结构：三层记忆。工作记忆（最近几轮原文，有 token 上限）、情景摘要（旧轮次压缩，有损）、长期事实（从对话里抽出来的结构化事实，无损，pinned 的永远进上下文）。
2. 再说排查路径，它是一条固定流水线，每一步看 trace 里对应的事件：
   - 用户真的说过吗？（`turn.start`）
   - 写入侧：抽取到长期记忆了吗？（`memory.fact_upsert`）没有 → 抽取规则漏了
   - 读取侧：第 20 轮请求的上下文里有没有它？（`context.built` 的 memory_block / included_turns）
     - 有 → 不是记忆层的问题，是提示词或模型的问题，用同一上下文离线重放验证
     - 没有，且事实未 pinned → 召回没召回到（打分问题 / 该 pinned 没 pinned）
     - 没有，原文轮次被压缩且摘要里没有 → 压缩时丢了
     - 没有，原文被预算裁掉 → 裁剪逻辑没把 pinned 事实放进关键信息块
3. 每种结论对应一个修法：补抽取规则 / 标 pinned / 压缩时把 pinned 作为 must_keep 传给摘要器并在压缩后用代码校验补回 / 关键信息块不参与预算竞争。

**项目里的证据**：`memory/diagnose.py::diagnose_missing_fact` 就是这条流水线的代码；`examples/02_memory_turn20.py` 跑 20 轮并输出诊断；`test_turn_20_naive_forgets_*`（结论 not_extracted）、`test_turn_20_guarded_remembers_*`（present_in_context）、`test_diagnosis_distinguishes_not_recalled_*`。

**追问预判**
- "上下文窗口塞爆了怎么办？" → 两个独立机制：工作记忆超高水位就压缩（`MemoryConfig.working_high_water_tokens`），每次请求再按预算裁（`AgentConfig.context_budget_tokens`），裁剪以完整轮次为单位、永不拆开工具调用组。
- "压缩有损怎么保证关键信息不丢？" → 压缩输入带 must_keep，输出后 `ensure_facts_present` 用代码校验补回，压缩事件记 trace（哪些轮被压、补回了什么）。
- "跨会话呢？" → 长期事实层按用户持久化，会话开始时加载 pinned 事实。

## Q5 大模型不确定，Agent 行为跑偏怎么兜底？死循环 / 内容安全 / 成本控制

**在考什么**：你是靠"模型听话"还是靠"代码卡住它"。评论区的追问是关键：只有步数上限等于烧完预算才停。

**回答骨架**
1. **死循环**：最大步数只是最后一道闸。之前要有三种更早的检测：同工具同参数连续调用（第 2 次提醒、第 3 次强制收尾）、同参数累计调用（防 A-B-A-B 交替）、连续 N 次结果哈希相同（无进展）。触发后不是硬掐断，而是进入收尾模式：下一次调用不给工具，要求模型用现有信息作答；模型还要调工具就转人工。
   数字：同一个固执模型、同一个上游故障，只有 max_rounds=30 时 31 次调用 40,970 token；同参数检测 4 次调用 2,792 token。而且步数越多每步越贵（上下文在长），消耗是二次方增长。
2. **内容安全**：出向审核（规则：违禁词、PII；再可插拔 LLM 审核），动作分 pass / redact / block；入向脱敏（模型可能把用户手机号塞进搜索工具参数发给第三方）。审核判定记 trace，误杀率能复盘。
3. **成本**：三级预算（单请求输入由上下文预算裁剪、单轮累计、会话成本硬上限），到 80% 进收尾模式而不是半截掐断；提示词缓存（稳定前缀在前、波动内容在后、移动断点）；上下文裁剪与压缩。
4. 一套完整方案还要有：日志重放、关键节点断言、Bad Case 闭环（见 Q5b）。

**项目里的证据**：`guard/loop_detector.py`、`agent.py`（`force_final` 收尾模式）、`guard/content_filter.py`、`guard/budget.py`；`examples/03_loop_guard.py`。

**追问预判**
- "为什么不直接在第 2 次相同调用就停？" → 有些工具第二次真的会不一样（刚写入后再读）。第 2 次提醒、第 3 次停是经验值，`LoopPolicy` 可调，Bad Case 回归保证调参不倒退。
- "缓存什么时候失效？" → 断点之前任何字节变化：系统提示里的时间戳、未排序的 JSON、工具列表顺序抖动。项目里工具列表按名字排序（`ToolRegistry.schemas`），系统提示分两块，断点只打在稳定的第一块上，会变的记忆块是第二块（`anthropic_client.py::to_anthropic_system`）。

## Q5b 日志重放机制、关键节点断言、Bad Case 闭环复盘

**回答骨架**
1. **日志重放**：trace 记录每次模型请求指纹与响应、每次工具入参与结果。忠实重放 = 模型和工具都从记录取，不用真模型不用真下游就能单步复现一个线上坏结果；what-if 重放 = 工具结果用记录、模型用刻画其行为的策略、守护层换新配置，验证"如果当时有这条规则会在第几步停"。
2. **关键节点断言**：在确定性的位置用代码卡模型：写操作之前（退款订单号必须来自查询结果，不能是模型编的）、最终回复之前（非空）、压缩之后（pinned 事实还在）。hard 失败转人工，soft 只记录。
3. **Bad Case 闭环**：线上坏结果 → 抽象成 Bad Case 文件（复现条件 + 用户输入 + 修复后必须满足的断言）→ 永远跑的回归。"修好了"变成一个断言而不是一句话。

**项目里的证据**：`observability/replay.py`、`observability/badcase.py`、`badcases/*.json`、`guard/assertions.py`；`test_replay_badcase.py`（含"同一用例换回事故前配置必须不通过"的区分度测试）。

## Q6 为什么选状态机而不是线性 Chain？分支执行失败怎么回滚？

**在考什么**：有没有真的上线过一个多步流程，处理过中间某步失败。

**回答骨架**
1. Chain 只有"下一步"，没有分支、循环、恢复，也没有"这一步失败了该怎么办"的语义；一个环节抛异常整条链就断。
2. 状态机把这些变成节点的显式属性：节点级重试策略（只重试可重试异常）、分支边（根据 state 判定下一节点）、可选节点（失败只标记 degraded，不拖垮主流程）、超时、checkpoint（崩了从断点恢复而不是重跑，重跑会重复退款）。
3. 回滚 = Saga 补偿：必需节点失败时，已完成的有副作用节点按逆序执行补偿动作。补偿是冲正不是删除（账务不可篡改）；补偿本身失败要 critical 告警人工介入。
4. 防单点故障拖垮链路：可选节点降级 + 节点超时 + 边判定的流转上限（防边逻辑死循环）。

**项目里的证据**：`workflow/state_machine.py`、`workflow/example_flow.py`；`examples/04_workflow_refund.py` 七个场景；`test_workflow.py`。

**追问预判**
- "为什么不用 LangGraph？" → 可以用，问题是你能不能讲清它替你做了什么、没做什么（补偿逻辑、幂等、checkpoint 存储通常还是要自己设计）。
- "resume 之后节点会不会重复执行副作用？" → checkpoint 在节点成功后写；恢复从 next 开始；节点内部仍应幂等（示例里 auto_refund 用 ledger 记录）。

## 评论区追问 A：讲一次真实的线上故障，从怎么发现、怎么定位到最后怎么修

"只跑通过 demo 的人讲不出发现那一环。"发现靠的是**指标和告警**，不是用户投诉。

回答结构（详见 `docs/07`）：
1. **发现**：什么指标、什么阈值、什么时间触发了什么告警（没有这个指标会怎样）。
2. **定位**：拉了哪条 trace、按什么维度聚合、看到了什么模式、和什么变更对上了时间。
3. **修复**：止血（分钟级）、短期修复（当天）、根因修复（当周）、防复发（回归用例 + 新告警）。
4. **数字**：修复前后各一个数字。

本项目的 INC-0421 是构造的可复现案例；把 `examples/05_incident_replay.py` 亲手跑一遍、改坏再修好，讲的时候才有细节。
