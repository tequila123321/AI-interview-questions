# 01 · 工具层：把"失败"当成一等公民

对应代码：`agentkit/tools/`，测试：`tests/test_tools_executor.py`、`tests/test_retry.py`，示例：`examples/01_tool_failures.py`。

## 1. 先分类：错误来自谁，决定了该怎么办

| kind | 来源 | retryable | 执行器动作 | 模型该做什么 |
|---|---|---|---|---|
| `invalid_args` | 模型给的参数不符合 schema | 否 | 不调用；把字段级错误放进信封 | 按 details 修正参数重调；缺信息先问用户 |
| `timeout` | 下游超时 | 是 | 幂等则按退避重试；耗尽后信封改为不可重试 | 不再重试，告知用户或转人工 |
| `transient` | 5xx / 连接重置 / 限流 | 是 | 同上，尊重 Retry-After | 同上 |
| `permanent` | 404 / 业务规则拒绝 | 否 | 不重试，直接降级 | 按 hint 处理（例如核对订单号） |
| `invalid_result` | 下游返回结构不符合契约 | 否 | 降级 + 高优告警 | 不要据此编造 |
| `circuit_open` | 最近连续失败太多 | 否 | 不打下游，直接降级 | 告知用户稍后再试 |
| `unknown_tool` | 模型调了不存在的工具 | 否 | 信封附可用工具列表 | 换工具 |

代码：`tools/errors.py`。每个异常类自带 `kind` / `retryable`，`to_dict()` 变成信封里的 error。

## 2. 执行链路（`ToolExecutor._execute`）

```
模型的 ToolCall
 → 1 registry.get         未知工具 → UnknownTool
 → 2 args_model 校验       失败 → ToolArgsInvalid（不重试）
 → 3 会话级缓存            幂等（idempotent=True）且配了 TTL 且命中 → 直接返回 cached=True；写操作配了 TTL 也不缓存
 → 4 熔断器 allow()        open → CircuitOpen → 降级
 → 5 run_with_retry(run_with_timeout(handler))
       只有 spec.idempotent 才用 spec.retry；非幂等用 NO_RETRY
 → 6 result_model 校验     失败 → ToolResultInvalid → 降级 + alert
 → 7 _degrade              fallback 默认值 / handoff_on_failure 转人工 / 结构化错误
 → 8 ToolOutcome.envelope()
```

每一步都有 trace 事件：`tool.call`、`tool.attempt`（含耗时）、`tool.retry`（含等待时间）、`tool.result`（含结果哈希和完整信封）、`alert`。

## 3. 重试：什么时候重试，怎么重试

`tools/retry.py::RetryPolicy`：

- **只重试 retryable 的异常**。`run_with_retry` 看异常对象上的 `retryable` 属性，永久错误立刻抛出（`test_only_retryable_errors_are_retried`）。
- **只重试幂等操作**。`refund_order.idempotent=False`，执行器一次都不重试（`test_non_idempotent_write_is_never_auto_retried_and_hands_off`）。写操作想安全重试要靠幂等键：同一个 `idempotency_key` 重复请求返回上次结果（`test_idempotency_key_makes_repeated_refund_safe`）。
- **指数退避 + 全抖动**：等待 = `uniform(0, min(max_delay, base × multiplier^(attempt-1)))`。抖动的目的是防止一批实例在同一毫秒重试把刚恢复的下游再打死。
- **尊重 Retry-After**：下游明确要求等多久就等多久，**不受退避上限 max_delay 影响**（否则下游让你等 60 秒你 5 秒就回去打它）；但有单独的 `max_retry_after_s`（默认 60s）封顶，防止被一个荒谬的值挂死（`test_retry_after_from_downstream_is_respected_beyond_backoff_cap`）。
- **重试有上限，且耗尽后要告诉模型"别再试了"**。`_degrade` 把 retryable 改成 false，message 追加"已自动重试 N 次"。否则模型看到 retryable=true 会自己再来一轮，等于把重试次数乘以模型的耐心。

## 4. 熔断：重试解决抖动，解决不了"下游挂了"

`CircuitBreaker` 三态：closed → 连续失败达到阈值 → open（直接拒绝）→ 冷却时间后 half_open（放一个探测）→ 成功回 closed / 失败回 open。

为什么需要它：下游持续失败时，每个请求都完整走一遍"超时 × 重试次数"，线程池和连接池被占满，本服务也跟着雪崩。熔断让失败变得便宜（`test_circuit_breaker_opens_after_consecutive_failures` 里第三次 `attempts=0`）。

熔断按工具粒度，一个工具坏了不影响别的工具。

## 5. 超时：最后一道防线在哪里

`run_with_timeout` 起一个 daemon 线程跑 handler，`join(timeout_s)` 后还活着就抛 `ToolTimeout`。要诚实说明三件事：
- **Python 杀不掉线程**：超时后工作线程仍在跑到结束，这里只是不再等它；下游要是卡 6 秒，这个线程就活 6 秒。
- **为什么是 daemon 线程而不是 ThreadPoolExecutor**：线程池的工作线程不是 daemon，解释器退出时会 join 它们，一个卡住的下游就让进程多活那么久；daemon 线程不会拖住进程退出。
- **真正的超时必须配在 I/O 客户端上**（httpx timeout、数据库 statement_timeout），或者用 asyncio + `wait_for`。这个包装保证的只是"调用方一定能在 timeout_s 内拿回控制权"（`test_real_timeout_guard_returns_control_quickly`），而且每次调用起一个线程，生产上应该用异步 I/O。

## 6. 结果校验：下游的错不能让模型背

`ToolSpec.result_model` 是 pydantic 模型，只声明**你依赖的字段**。上游多加字段不会失败；改名、缺失、类型变了才失败。失败的处理是降级 + `alert` 事件（严重度 high），因为这几乎总是意味着上游发布了不兼容变更。

事故前的 `lookup_order_v1` 没有 `result_model`，上游返回什么模型就看到什么（`test_v1_tool_passes_garbage_through_when_no_result_model`）。这就是 `docs/07` 事故的根因之一。

## 7. 降级矩阵：按工具的关键程度决定

| 工具 | 关键程度 | 最终失败时 | 配置 |
|---|---|---|---|
| get_weather | 非关键信息 | 给默认值 `{condition: "unknown"}`，信封标 degraded | `fallback=` |
| search_kb | 非关键信息 | 给空结果 | `fallback=` |
| lookup_order | 关键信息 | 结构化错误 + hint，让模型如实告知 | 无 fallback |
| refund_order | 关键写操作 | 转人工，绝不给"默认成功" | `handoff_on_failure=True` |

降级值必须标记（信封里 `degraded: true` + `note`），模型才能告诉用户"信息可能不完整"（`test_degraded_tool_result_is_surfaced_to_user`）。

## 8. 信封：模型看到的每一个字都会影响它的下一步

```json
{"ok": false, "error": {"kind": "permanent", "message": "订单 SO-999 不存在", "retryable": false,
 "hint": "订单号可能有误，请向用户核对订单号（格式 SO-数字），不要重复用同一个订单号查询"}}
```

- `retryable` 是给模型的明确信号，不是给程序员看的注释。
- `hint` 写的是"该做什么"，不是"发生了什么"。
- 错误文案里**不要出现 "retry"、"try again"** 之类的词，除非你真的希望模型重试。`docs/07` 的事故就是上游文案里的 "please retry later" 被原样透传导致的。
- `guard_note` 字段由守护层注入（连续相同调用的提醒），模型能看到自己在原地打转。

## 9. 模型层的错误处理（同样的思路）

`agent.py::_call_llm`：429 / 5xx / 连接与超时 → `LLMTransientError`，按 `AgentConfig.llm_retry` 退避重试（`test_llm_transient_errors_are_retried_with_backoff`）；4xx → `LLMPermanentError` 不重试；耗尽后不是抛异常炸掉请求，而是转人工（`test_llm_persistent_failure_hands_off_instead_of_crashing`）。模型拒答（`stop_reason == "refusal"`）用兜底话术。

Anthropic 适配器里把 SDK 自带重试关掉（`max_retries=0`），统一在 Agent 层重试，这样每一次重试都有 trace 事件。

## 10. 面试时的一句话版本

"工具层我按错误来源分三类：模型的错还给模型改，下游抖动幂等重试带抖动，下游确定性失败直接降级；重试之外有熔断，结果有 schema 校验，降级按工具关键程度分默认值和转人工；模型看到的永远是带 retryable 和 hint 的结构化信封。"
